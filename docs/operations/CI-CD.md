# CI/CD architecture

This document defines the continuous integration, security, documentation, migration, and release-candidate automation for Digital Ham Radio Logbook.

The goal is to keep pull-request feedback fast and explicit while preserving the project's strongest guarantees: locked Rust builds, historical SQLite migration coverage, deterministic release discipline, local/offline behavior, and exact-binary packaging.

## Principles

- workflows have one clear responsibility;
- permissions are minimal and read-only unless a future publishing workflow explicitly needs more;
- external GitHub Actions are pinned to full commit SHAs;
- the Rust toolchain is pinned in `rust-toolchain.toml`;
- shared Linux/Rust setup lives in `.github/actions/setup-rust-linux/action.yml`;
- CI validates source; it does not create tags or publish GitHub Releases;
- the release-candidate workflow builds the release binary exactly once and derives all Linux packages from that binary;
- documentation validation is network-independent and checks repository-relative links in live documents;
- historical documentation remains a snapshot and is not forced to rewrite old contextual links.

## Workflows

### `ci.yml` — pull-request gate

Runs on pushes and pull requests targeting `main` or `develop`, plus manual dispatch.

Jobs:

- **Quality**
  - repository whitespace check;
  - `cargo fmt --check`;
  - `cargo check --locked`;
  - Clippy with warnings denied.
- **Tests and build**
  - `cargo test --locked`;
  - `cargo build --locked`.
- **Linux packaging smoke**
  - POSIX shell syntax;
  - `packaging/linux/smoke-test.sh`.

These names are intentionally stable because they are suitable required status checks.

## `migrations.yml` — historical database compatibility

Runs the exact migration preservation test for schemas 0 through 7.

Unlike the previous matrix, the workflow installs Linux dependencies and Rust only once. Each source schema remains a separate named step so a failure still identifies the historical version immediately.

This keeps the visibility of the old matrix while avoiding eight independent Ubuntu setup/build cycles.

## `docs.yml` — documentation integrity

Runs `scripts/check-doc-links.py`.

The validator enforces:

- only `README.md` remains as Markdown in the repository root;
- the professional `docs/` category structure exists;
- live documentation files exist;
- repository-relative links in live documentation resolve.

External URLs are intentionally not tested by CI because third-party availability would create false negatives.

Historical release notes, old QA snapshots, `SPEC.md`, and `PROGRESS.md` are preserved as historical context and are excluded from link-freshness enforcement.

## `security.yml` — dependency advisories

Runs RustSec against `Cargo.lock`:

- weekly;
- manually;
- when Cargo manifests, lockfile, toolchain pin, or the security workflow change.

The workflow uses a full-SHA-pinned RustSec action and read-only repository permissions.

Dependency update PRs are also generated by Dependabot for Cargo and GitHub Actions, targeting `develop`.

## `release.yml` — exact release-candidate artifacts

This workflow is **manual only**.

It requires the operator to enter the exact version expected in `Cargo.toml`. It does not tag, merge, or publish a GitHub Release.

The workflow:

1. checks out the exact selected ref with full history;
2. verifies the requested version and release-note document;
3. runs locked formatting, compile, Clippy, and test gates;
4. validates schemas 0–7;
5. runs packaging syntax and smoke checks;
6. downloads a pinned `appimagetool` and pinned AppImage runtime and verifies both SHA-256 hashes;
7. calls `make-release.sh` once, producing the release binary and tarball;
8. derives `.deb` and AppImage from that exact already-built binary;
9. verifies every package contains byte-identical application binary content;
10. verifies all sidecar checksums;
11. writes `BUILD-METADATA.txt` and aggregate `SHA256SUMS`;
12. uploads the entire `dist/` directory as a GitHub Actions artifact.

The uploaded artifact is a release candidate for manual QA and explicit maintainer approval. It is not a published release.

## Recommended repository rulesets

Rulesets are repository governance and are configured in GitHub settings, not in these workflow files.

A recommended `develop` ruleset should:

- require pull requests;
- block force pushes;
- require the following status checks:
  - `Quality`;
  - `Tests and build`;
  - `Linux packaging smoke`;
  - `Historical schemas 0-7`;
  - `Documentation integrity`;
- optionally require the branch to be up to date before merge.

A recommended `main` ruleset should be at least as strict and should preserve the project's explicit release authorization process.

The automated security workflow is intentionally not a universal required PR check because it only runs on dependency-sensitive changes and on schedule.

## What CI does not replace

Automation does not replace:

- manual visual QA at `1050×680`;
- real-world UI inspection in System, Light, and Dark;
- representative upgrade drills using released artifacts;
- release authorization;
- tag creation;
- final GitHub Release publication.

Those remain governed by `docs/releases/RELEASE-CHECKLIST.md`.
